# ADR-0002: RO-Style 2D Sprite Rendering in 3D

## Status
Accepted

## Date
2026-05-28

## Context

### Problem Statement
How to render 2D sprites in a 3D environment (Three.js) to achieve the same visual result as Ragnarok Online's "2.5D" look. The sprites have baked perspective (generated by SpriteCook) and must appear to stand upright on the 3D terrain while maintaining correct depth ordering and transparency.

### Constraints
- Camera is orthographic, fixed at position (0, 14, 16), only translates to follow the player — it never rotates
- Sprites use sprite-sheet textures with UV animation for frame cycling (idle, walk, attack, hit, dead)
- Each entity has 8 directional animation sets (N, NE, E, SE, S, SW, W, NW) with frame timing in milliseconds
- Sprites must correctly occlude each other based on distance from camera (Y-sort Z-order)
- SpriteCook images have baked perspective — they are pre-rendered from a specific isometric angle
- All sprite materials use transparency; z-fighting with terrain and other sprites must be avoided

### Requirements
- Sprites must appear to stand upright on the 3D ground plane
- Sprites must not use dynamic billboards that break the baked perspective
- Frame animation must cycle correctly per entity (different frames per AnimState)
- Sprites must sort correctly by depth (further = drawn first)
- Selection indicators, HP bars, and name tags must render correctly on top of sprites
- Must support both player sprites (Sprite.tsx) and enemy/NPC sprites (SpriteEntity.tsx)
- Zero new lint errors

## Decision

Use a **fixed-angle sprite plane** tilted toward the camera at `-atan2(14, 16)` radians (~-41°) around the X axis, with NO dynamic billboard. Directional animation frames are selected by entity facing direction + camera angle. Depth sorting is handled by Y-sort on the entity container.

### Key Interfaces

#### `Sprite.tsx` — Player / NPC / Remote Player
```tsx
const CAMERA_TILT = -Math.atan2(14, 16); // ≈ -0.7188 rad ≈ -41°

<Sprite
  entityId="novice_m"
  state="walk"
  direction="S"
  width={1.5}
  height={1.5}
  opacity={1}
  color="#ffffff"
>
  {children} {/* optional overlays */}
</Sprite>
```

#### `SpriteEntity.tsx` — Enemy / Monster
```tsx
<SpriteEntity
  entityId="poring"
  position={{ x: 5, y: 0.5, z: 3 }}
  direction="S"
  animState="idle"
  scale={1}
  isDead={false}
  isSelected={false}
  hpBar={{ current: 50, max: 100 }}
  nameTag="Poring"
/>
```

#### `SortedEntities` — Depth-sorted container
```tsx
<SortedEntities entities={entityList} />
// Internally sorts by depth = z + y + x × 0.1
```

### Sprite plane geometry reference

```
Default PlaneGeometry (XY plane, facing +Z):
     (-w/2, +h/2, 0) ───── (+w/2, +h/2, 0)
                      │   │
                      │   │
     (-w/2, -h/2, 0) ───── (+w/2, -h/2, 0)

After rotation [CAMERA_TILT, 0, 0]:
     Top (+Y) → tilts toward -Z (away from camera)
     Bottom (-Y) → tilts toward +Z (toward camera)
     
     Camera at (0, 14, 16):
       Normal (0, 0, 1) → (0, sin(41°), cos(41°)) ≈ (0, 0.656, 0.755)
       This normal points toward the camera at (0, 14, 16)
```

## Alternatives Considered

### Alternative 1: Dynamic Billboard (`@react-three/drei <Billboard follow>`)
- **Description**: Sprite plane always faces the camera dynamically using `Billboard` with `lockX={true} lockY={false} lockZ={true}`
- **Pros**: Sprite always faces camera regardless of camera position/angle; simple to implement
- **Cons**: Breaks baked perspective — the pre-rendered SpriteCook image expects a fixed viewing angle. Dynamic rotation creates visual inconsistency where the sprite "floats" unnaturally when camera changes position. The `lockY={false}` causes horizontal rotation which makes the sprite appear to slide/follow the camera in a way that undermines the 2.5D illusion
- **Rejection Reason**: Our camera is fixed orthographic (never rotates); dynamic billboard adds unnecessary rotation that breaks baked perspective with zero visual benefit

### Alternative 2: Three.js `Sprite` Object
- **Description**: Use Three.js built-in `Sprite` class which always faces the camera 100%
- **Pros**: Auto-facing, simple API, uses `SpriteMaterial` for direct texture rendering
- **Cons**: Three.js `Sprite` always orients itself perpendicular to the camera direction, which makes it impossible to control the tilt angle. Cannot be easily combined with HP bars, selection rings, and other child elements in a single coordinate space. No control over UV animation for sprite sheets
- **Rejection Reason**: Loss of control over tilt angle makes baked perspective mismatch unavoidable

### Alternative 3: No Tilt, Front-Facing Plane Only
- **Description**: Use planeGeometry facing +Z with no rotation at all; rely on direction-based frames for visual variety
- **Pros**: Simplest approach, no additional transform math
- **Cons**: A plane facing +Z is edge-on from the camera at (0, 14, 16); even with `DoubleSide` it appears as a thin vertical strip rather than a full sprite. The baked perspective would be completely wrong
- **Rejection Reason**: Sprite is nearly invisible from the isometric camera angle without tilt

### Alternative 4: Screen-Space Billboard (custom shader)
- **Description**: Write a custom vertex shader that always faces the sprite toward the camera in screen space while maintaining world position
- **Pros**: Full control over the facing behavior; could potentially match baked perspective
- **Cons**: Requires shader code, custom material, more complex to integrate with R3F. Provides no benefit over the fixed-tilt approach since the camera never rotates
- **Rejection Reason**: Over-engineering for a problem solved by a simple fixed rotation

## Consequences

### Positive
- Sprites correctly appear upright from the isometric camera perspective
- Baked perspective from SpriteCook images is preserved
- Directional animation frames display correctly according to entity facing
- Depth-sorting (Y-sort) produces correct occlusion between entities
- HP bars and name tags render at correct world positions (untilted)
- No dependency on `@react-three/drei Billboard`, reducing bundle size
- `depthWrite={false}` on all sprite materials prevents transparent sorting artifacts
- `DoubleSide` rendering ensures sprites are visible regardless of the exact camera angle

### Negative
- Fixed tilt angle assumes the camera never changes its elevation — if the camera system is ever modified to allow rotation or elevation change, the tilt angle must be recalculated or a dynamic solution must replace the fixed rotation
- The `CAMERA_TILT` constant is hardcoded as `-Math.atan2(14, 16)` (matching current camera at `[0, 14, 16]`) — a camera configuration change breaks the sprite rendering

### Risks
- **Camera elevation change**: Low risk — the orthographic camera is designed to be fixed; elevation is part of the game's visual identity. **Mitigation**: If camera elevation changes, update `CAMERA_TILT` in both `Sprite.tsx` and `SpriteEntity.tsx` to match the new `y` and `z` values
- **Transparency sorting**: The Y-sort depth formula (`z + y + x × 0.1`) is a heuristic; entities at very similar depths may flicker. **Mitigation**: Y-sort is sufficient for an isometric game with discrete positions; flickering is unlikely unless entities occupy nearly identical world positions
- **Sprite bounds cutoff**: The tilted plane moves the sprite's top further from the camera (toward -Z) and bottom closer (+Z); sprite images that fill the canvas edge-to-edge may clip against terrain at extreme angles. **Mitigation**: Sprite sheet images should include padding (transparent border) to prevent visual clipping

## Performance Implications
- **CPU**: Minimal — each sprite is a single `useFrame` call checking elapsed time against animation duration; no per-frame matrix recomputation (tilt is baked into the scene graph)
- **GPU**: One draw call per sprite with `MeshBasicMaterial` (no lighting calculations); `depthWrite={false}` reduces GPU workload
- **Memory**: One `PlaneGeometry` per sprite instance; textures are cached globally in `spriteManager.ts` and reused across all instances of the same entity
- **Load Time**: Textures are loaded on first access; `prefetchEntity()` can preload all animation frames for an entity

**Already applied** — this ADR documents the current implementation after the fix. No migration steps required.

### Changes made (2026-05-28):
1. **`components/game/Sprite.tsx`**:
   - Removed `Billboard` import from `@react-three/drei`
   - Removed `billboard` prop from `SpriteProps`
   - Removed `DoubleSide` import (unused)
   - Added `const CAMERA_TILT = -Math.atan2(14, 16)` as module-level constant
   - Replaced `<Billboard follow lockX lockY={false} lockZ>` with `<group rotation={[CAMERA_TILT, 0, 0]}>`
   - Removed unused `useMemo` import

2. **`components/game/SpriteEntity.tsx`**:
   - Added `const CAMERA_TILT = -Math.atan2(14, 16)` inside component
   - Wrapped `<mesh>` (the sprite plane) in `<group rotation={[CAMERA_TILT, 0, 0]}>`
   - HP bar and name tag remain outside the tilt group (correct world-space positioning)

3. **`components/game/Player.tsx`**: Removed `billboard` prop from `<Sprite>` usage

4. **`components/game/RemotePlayers.tsx`**: Removed `billboard={false}` prop from `<Sprite>` usage

5. **`components/game/NPC.tsx`**: Removed `billboard={false}` prop from `<Sprite>` usage
